## Goals / Non-Goals

**Goals:**

- Screen 1 as the wireframe draws it, with every deviation written down (D2–D7, D9, D14, D16).
- The cards never depend on the network; the API status is extra information, not a gate.
- One error screen for the whole route table, so DIS-65/66 inherit it.

**Non-Goals (design level, besides the proposal's):**

- No data layer (no React Router loader, no React Query, no context): one page-local hook.
- No change to the API client, the theme tokens, `PageFrame`, `AppHeader`, `NotFoundPage` or the
  `jsdom-setup.ts` workarounds.
- No Playwright suite (DIS-75): the browser checks are the manual and end-to-end steps.

## Decisions

D1–D14 come from the `[enhanced]` description of DIS-60 (agent as lead engineer, ADR
`20261016-autonomous-workflow-run-entrega-2`, reviewable by the author). D15–D22 were taken while
proposing, D26–D31 while implementing, and D23–D25 while resolving the spec audit (run 1, `reports/2026-10-18-spec-audit.md`), which
also refined D3, D6, D9, D11, D17 and D19; all of them were added to the same description on 2026-10-18
("Decisiones D15–D25"). D32–D34 were taken while fixing the pre-merge review findings (task 14).

### D1 — An OpenSpec change with the new capability `project-picker`

The ticket marks it as an OpenSpec candidate. The capability holds Screen 1, the API-unavailable alert
and the app's error screen; `web-foundation`'s route requirement changes through a delta (D12, D15).

### D2 — The cards come only from the constant

`ProjectPickerPage` maps `SAMPLE_PROJECTS` on the first render, without waiting for anything. The
counts are the seed's (53/121/170/32), not the wireframe's illustrative ones (47/312/1 840/62).

### D3 — One card in Entrega 2 (deviation from the wireframe)

The wireframe draws acme-shop and task-api; the constant holds only acme-shop (PH-02: task-api arrives
with CM-HU-18). The page renders the cards of the constant, in its order (by name), in a `ul` with
`flex flex-wrap justify-center gap-…`: one card is centred; two sit side by side as in the wireframe.
Each card is `w-72` (the wireframe's 280 px). The 6 px top stripe alternates `bg-stripe` (even index)
and `bg-stripe-soft` (odd index), as the wireframe does; it is decoration (`aria-hidden` `div`). The
article is `text-left` (the wireframe aligns the card content left; `PageFrame`'s `main` is
`text-center`), while the heading, subtitle and indexing hint stay centred.

### D4 — Language and framework without versions (deviation)

The wireframe writes «PHP 8.2 / Laravel 11»; the constant has no versions and none is invented. Labels:
`php` → «PHP», `typescript` → «TypeScript», `laravel` → «Laravel», `fastify` → «Fastify», any other
identifier as is, `framework: null` → only the language. Icons from the wireframe: 🐘 for `php`, 📘 for
`typescript`, none otherwise; the count icons 📁 🔷 ↔ 📝. Every icon is an `aria-hidden` `span`
separate from the text, so the accessible text and `getByText` see «53 ficheros», not the emoji.

### D5 — Count format

A pure function `formatCount(n, singular, plural)` in `components/project-display.ts`: «1 fichero»,
otherwise plural; digits grouped in threes with U+00A0 from 1 000 up (`1840` → «1 840»). Not
`Intl.NumberFormat('es-ES')`: it does not group four-digit numbers and its output depends on the ICU of
the environment (jsdom/Node vs browser). The four counts are a `ul` of four `li` in the wireframe's
order (files, symbols, edges, commits), laid out as a 2×2 grid.

### D6 — Badges «indexado» and «listo»

The constant has no status field: every project in it comes from the indexed seed, so «✓ indexado» is
fixed (✓ `aria-hidden`, `text-success bg-success-soft`). «listo» means "the API answers and you can ask":
shown only after the health check resolved (`text-accent bg-accent-soft`), absent when the API is down
(the alert explains it). While the first check is pending the same slot shows «comprobando…»
(`text-ink-muted bg-canvas`, D23). No badge claims something the page does not know. The badges are
`span`s in one row whose height does not change when «comprobando…» gives way to «listo» or disappears.

### D7 — The «Explorar proyecto» link

A router `Link` (it navigates), styled as the primary button: `bg-accent text-on-accent rounded-button`
instead of the wireframe's `#4dabf7` (contrast, DIS-58 D4). Visible text «Explorar proyecto», arrow
`aria-hidden`, the project name in a `sr-only` span: accessible name «Explorar proyecto acme-shop», which
starts with the visible text (WCAG 2.5.3) and tells cards apart (2.4.4). `focus-visible` outline as in
`NotFoundPage`. Each card is an `article` with `aria-labelledby` its `h2`; the list is a `ul` with
`aria-label="Proyectos de muestra"`, so tests query everything by role.

### D8 — Health check in an effect, not in a loader

A React Router loader would block the cards until `/health` answered or timed out (5 s), and would force
revisiting the `Request` workaround of `jsdom-setup.ts` (DIS-58 D26). `useApiHealth()` (in
`pages/useApiHealth.ts`) starts in `checking`, calls `getHealth({ signal })` with the default limit and
moves to `available` or `unavailable`; any rejection other than its own abort (`ApiUnavailableError`,
`ApiError`, `RangeError`, anything else) is `unavailable`. The effect cleanup aborts the pending check,
which also covers `StrictMode`'s double mount in development (two requests in `dev`, one in tests and in
the build). No automatic retry: retrying is the person's action (DIS-58 D9).

### D9 — The API-unavailable alert (deviation: the wireframe does not draw it)

Between the subtitle and the cards, so it is read before entering a project. `ErrorBanner` (props:
message content and `onRetry`), role `alert`, `warning-*` colours with a `warning-border` border, ⚠
`aria-hidden`, the text of the spec (`make up` in `<code>`, D24) and a `type="button"` «Reintentar»
styled as the primary button (D24). During a retry the alert stays, the button reads «Reintentando…»
and keeps the focus; repeated presses are ignored (no `disabled`, which would drop the focus to `body`).
If the retry succeeds the alert disappears and the focus (unless the person moved it, D32) moves to the `h1` (`tabIndex={-1}`: focusable by
script, never reached with Tab), so a keyboard user is not left on `body`. If it fails, the button reads
«Reintentar» again and nothing else changes. "la API", as in `readme.md`.

### D10 — Constant ↔ seed coherence: reuse the existing test

`tests/unit/seed/sample-projects-coherence.spec.ts` (DIS-92) already compares ids and the four counts
with `seeds/graph-dump.sql` and fails when one is regenerated without the other; its header says DIS-60
relies on it. The DoD "coherence test green" is met by it; the spec cites it and no second test is
added.

### D11 — The app's error screen (follow-up #5 of DIS-58)

A pathless root route wraps the three routes and declares `errorElement: <RouteErrorPage />` (no
`element`: React Router renders the `Outlet`). `RouteErrorPage` uses `PageFrame`: `h1` «Algo ha
fallado», the line of the spec and a `Link` «Volver a la selección de proyecto» to `/` (the
`NotFoundPage` style). It never shows the error's message or stack (it does not call
`useRouteError()` for display). A render error in the root route itself is not covered (it has no
element). The scenario is tested by building, in the test, a table whose root route is `routes[0]` with
one more child `{ path: '/test-only-boom', element: <Boom /> }`; axe checks the same screen in
`tests/a11y/project-picker.a11y.test.tsx` (no URL leads to it, so the existing gate cannot reach it).
`RouteErrorPage` and `NotFoundPage` would repeat the same link markup and classes
(`NotFoundPage.tsx:13-19`): the refactor step (8.1) may extract one shared link component used by both,
with no behaviour change and no test edit.

### D12 — `web-foundation` delta and the placeholder test

The route requirement stops describing `/` as a placeholder; its scenario "The root path shows the
Screen 1 placeholder" leaves the spec and its checks move to `project-picker` → "Screen 1 shows the
sample projects without waiting for the API". Its test in `router.test.tsx` is therefore removed: a
specified behaviour change, not a fix to make the suite green. The other tests of `router.test.tsx` and
`tests/a11y/smoke.a11y.test.tsx` are not edited; the existing gate scans the real Screen 1 at `/`.

### D13 — Accessibility of both states

`tests/a11y/project-picker.a11y.test.tsx` (new) scans `/` with `fetch` answering `ok` (after «listo»
appears) and with `fetch` rejecting (after the alert appears), and the error screen; same
`lang="es"`/title setup as the existing gate. Keyboard order and visible focus are checked by hand in
the browser (steps 10–11 and `/show-spec-working`).

### D14 — «+ Indexar mi propio repositorio» (deviation of the requirements line)

The wireframe text, in `text-accent`, not underlined, as a `p` (not a link or button: gate question 2).
Below it the command in `<code>` (`text-ink-muted bg-canvas`) and the line of the spec. The wireframe's
«Requiere Docker · PHP 8.2+ o Node 20+» is no longer true: indexing needs no PHP (Tree-sitter
WebAssembly, readme §1.4) and TypeScript is not indexed yet (CM-HU-18). The wireframe's dashed separator
(`hr` with `border-dashed`) and order are kept. The footer «PANTALLA 1 — Selección de proyecto» is a
wireframe annotation and is omitted (DIS-58 D5). The wireframe's grey requirements text (`#adb5bd`) and
subtitle (`#868e96`) fail 4.5:1 on white; both use `text-ink-subtle` (`#6c757d`, in the theme table).

### D15 — REMOVED + ADDED instead of MODIFIED for the route requirement (taken while proposing)

OpenSpec refuses a MODIFIED block that drops a scenario of the current spec (`openspec validate`:
"MODIFIED … omits scenario(s) the current spec still has"), and there is no scenario-level removal. So
the delta removes "Routes of the web client" and adds "Routes and screens of the web client" with the
same text for `/p/{projectId}`, the not-found screen and the development server, `/` pointing to
`project-picker`, and the error-screen wrapping. "Component test environment" is MODIFIED only in the
wording of its scenario ("renders Screen 1"); its test keeps its name and body.

### D16 — The requirements line names Git (taken while proposing)

`readme.md` §1.4 says indexing needs Git 2.45.1 or later (or 2.43.4/2.44.1). The line becomes
«Desde la terminal · requiere Docker, Node 20+ y Git 2.45.1+ · por ahora solo PHP» (refines `[enhanced]`
D14, which named only Docker and Node). The maintenance versions stay in the readme.

### D17 — The hook's states and the retry guard (taken while proposing)

`useApiHealth()` returns `{ status: 'checking' | 'available' | 'unavailable', retrying, retry }`.
`checking` is only the first check (the «comprobando…» badge). `retry()` keeps `status` as `unavailable`
while the new check runs (so the alert and its focused button stay), sets `retrying` (the button's
«Reintentando…» label) and is a no-op while any check is in flight (a ref, not state, so two clicks in
the same tick are also ignored). Each check owns an `AbortController`; unmount aborts the current one. The page moves the focus
to the `h1` in an effect that runs only when a retry (not the first check) ends in `available`.

### D18 — The time-limit scenario under fake timers (taken while proposing)

"A health check that never answers shows the alert after its time limit" uses
`vi.useFakeTimers({ toFake: ['setTimeout', 'clearTimeout'] })` before rendering (React's scheduler uses
`setImmediate`/`MessageChannel`, left real), `await act(() => vi.advanceTimersByTimeAsync(…))` and
synchronous `queryByRole` (RTL's `findBy*` polls with timers it does not know are fake under Vitest).
`vi.useRealTimers()` in `afterEach`.

### D19 — Existing tests that render `/` without stubbing `fetch` (taken while proposing)

`router.test.tsx` ("An unknown path… leads back", "Rendered output does not leak between tests") and
`smoke.a11y.test.tsx` render Screen 1 with Node's real `fetch`. Under jsdom that call rejects with a
`TypeError`: Node's `fetch` refuses jsdom's `AbortSignal` (`docs/project-context.md` → Testing) and has
no base URL for the relative `/health`; so the page shows the alert; none of them
asserts its absence, and the cleanup unmounts the page (aborting the check). These tests are not edited
(no test may be edited to make the suite pass). If React prints `act(...)` warnings from that late state
update, they are recorded in the step 9 report, not silenced. The new tests always stub `fetch`.

### D20 — File layout and scenario-to-test mapping (taken while proposing)

`pages/ProjectPickerPage.tsx`, `pages/useApiHealth.ts`, `pages/RouteErrorPage.tsx`,
`components/ProjectCard.tsx`, `components/ErrorBanner.tsx`, `components/project-display.ts`
(frontend-standards §2: `pages/` route screens, `components/` reusable pieces). Tests, named exactly as
the scenarios: the two display scenarios in `components/project-display.test.ts` (Node); the cards,
keyboard, API-status and indexing-hint scenarios in `pages/ProjectPickerPage.test.tsx`, rendering the
real `routes` in a memory router; the error-screen scenario in `pages/RouteErrorPage.test.tsx`; the two
accessibility scenarios in `tests/a11y/project-picker.a11y.test.tsx`; "The cards show the seed's
figures" is validated by command. Every new export has TSDoc.

### D21 — Console noise of the error-screen test (taken while proposing)

React and React Router log a caught render error to `console.error`. The error-screen tests spy on
`console.error` with an empty implementation for that test only (restored in `afterEach`), and assert
nothing about it; the behaviour is what the spec asserts.

### D22 — No new dependency (taken while proposing)

Everything used is installed since DIS-58 (`react-router` 7, Tailwind 4, `@testing-library/react`,
`@testing-library/user-event`, `axe-core`, `jsdom`). No `npm install` runs in this change, so the
dependency vetting of the autonomous run does not apply; the step 9 report records it.

### D23 — Explicit checking and retrying states (spec audit run 1, F1)

`docs/frontend-standards.md` §2 ("Loading and error states are explicit and rendered, never silent") and
§5 (loading state in the DoD). The cards are not loading (they are static), but the API status is: up to
5 s for the first check and an open-ended retry. So the first check shows the badge «comprobando…» in
the slot of «listo» on every card, and a pending retry changes the alert's button to «Reintentando…».
Alternatives rejected: a spinner (motion, a new asset, no text), `aria-busy` alone (invisible), or a
page-level status line (moves the layout when it disappears). The ellipsis is U+2026.

### D24 — Colours inside the alert (spec audit run 1, F2)

Only the pairs of the `web-foundation` theme table may carry text. The «Reintentar» button is the
primary button (`bg-accent text-on-accent rounded-button`, white on `#1971c2`, with the `focus-visible`
outline of the links), not a `warning`-coloured one (no listed pair); the `make up` code and the ⚠ inherit
`text-warning-ink` on `bg-warning-soft` (`#5c3d00` on `#fff9db`, listed), with no own background.

### D25 — The first check never moves the focus (spec audit run 1, F4)

Moving the focus when the page loads would interrupt a screen-reader user who has started reading; the
alert's role already announces the failure. Only a successful retry moves the focus (to the `h1`),
because then the focused button disappears.

### Taken while implementing (D26–D31)

Agent decisions during `/opsx:apply` (autonomous run, 2026-10-18), added to the `[enhanced]` description of
DIS-60.

- **D26 — Label tables are `ReadonlyMap`s.** The web compiles with `lib: ES2020`, which has no
  `Object.hasOwn`; a `Map` looks an identifier up without reaching `Object.prototype` (an identifier such
  as `constructor` is written as it is). The digit separator is written `'\u00a0'` in the source, never as
  the raw character, and the tests compare it by code point.
- **D27 — The shared link of D11 was extracted.** `components/BackToPickerLink.tsx` renders «Volver a la
  selección de proyecto» for `NotFoundPage` and `RouteErrorPage` (same markup and classes); no test
  changed.
- **D28 — The card takes the API status type from the hook.** `ProjectCard` imports `ApiHealthStatus` from
  `pages/useApiHealth.ts` as a type only (no runtime dependency from `components/` to `pages/`), so the
  three states are declared once. The article is named by `aria-labelledby` on its `h2` (`useId`); the
  language icon inside the `h2` is `aria-hidden`, so the name is the project's name.
- **D29 — TDD phases run inline.** This unattended step has no Task tool to start the `tdd-*` subagents, so
  each scenario went red → green → refactor inline with the same contract. Tests that passed as soon as
  they were written (2.4, 3.3, 3.5–3.7, 6.1) were shown to fail with a temporary change of the production
  code, reverted at once (step 9 report).
- **D30 — Targeted mutation run outside Stryker's configuration.** `packages/web/**` stays out of
  `stryker.config.json` (DIS-58 D25, D22 here); a one-off configuration outside the repository mutated the
  eight new or changed web files: 84.46 % (break threshold 80). The survivors are recorded in the step 9
  report.
- **D31 — axe's canvas message is recorded, not silenced.** Scanning Screen 1, axe probes the card's emoji
  with a canvas that jsdom lacks and prints `Not implemented: HTMLCanvasElement.prototype.getContext` to
  stderr; it still reports zero violations. Installing `canvas` would be a new dependency (D22) and
  stubbing it would change `jsdom-setup.ts` (non-goal).

### Taken in the pre-merge review (D32–D34)

Agent decisions while fixing the findings of task 14 (reports `reports/2026-10-18-show-spec-working.md`,
`reports/2026-10-18-verify-against-spec.md`, `reports/2026-10-18-adversarial-review.md`), added to the
`[enhanced]` description of DIS-60 and to the spec through the addendum of `reports/2026-10-18-spec-audit.md`.

- **D32 — A successful retry moves the focus only when it was lost.** The reason to move it to the `h1`
  (D9, D17) is that the focused button disappears; if the person moved the focus elsewhere while the retry
  was pending (for example, tabbed to «Explorar proyecto»), taking it away is worse than leaving it. The
  page's effect moves the focus only when `document.activeElement` is `body` or `null` (the browser and
  jsdom put it on `body` when the focused button is removed). Spec "API status on Screen 1" and its new
  scenario "A successful retry leaves the focus where the person moved it".
- **D33 — The guard against an aborted check is tested under `StrictMode`.** No other render can observe
  it: after leaving the page nothing is left to show. Mounting the real routes inside `StrictMode` (as
  `main.tsx` does) aborts the first check while the page stays mounted, so a missing guard shows the alert
  with the API still checking. New scenario "A check the page cancels itself changes nothing on the
  screen"; it closes the mutation survivor of the step 9 report.
- **D34 — The alert wraps on narrow screens.** The ⚠ and the message share a box of at least `12rem`
  (`min-w-48 flex-1`) and the alert is `flex-wrap`: on a desktop the button stays on the message's row, on
  a phone it goes below the message instead of squeezing it into a 110 px column. The alert's text content
  and order do not change (layout only; checked in the browser at 320 and 1 280 px).

## Risks / Trade-offs

- [The existing a11y gate scans `/` while the real `fetch` may flip the page to the alert during the
  scan] → the alert is itself accessible (D13 scans it deterministically); a flaky gate would show as
  an axe violation on `/` and is fixed in this change by making the page's state settle (never by
  editing the gate).
- [`StrictMode` sends two `/health` requests in development] → harmless (the first is aborted); recorded
  in the manual test.
- [The «listo» badge says "the API answers", not "this project can be asked" (it does not call `/ask`)]
  → accepted: the precise per-project state belongs to Screen 2 (DIS-65); the alert text says what is
  missing when the API is down.
- [The page shows a stale state if the API stops after the check] → accepted (no polling, non-goal);
  Screen 2 reports its own failures.
- [The error screen hides the error detail] → the console keeps it for developers; the screen is for the
  person.

## Migration Plan

Additive in `packages/web` except `router.tsx` (the table gains a root route) and the removed
placeholder test. Rollback = revert the PR; no data, no API, no dependency change.
