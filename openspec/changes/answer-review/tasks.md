## 4. Panel

This group is done by independent agents launched by the workflow, outside the apply: reviewer 1 (Opus) and reviewer 2 (Sonnet), blind to each other; then the recording agent; then a resolver (Opus, fresh context). The apply does not do these tasks. Every rule below is fixed before any judgement (design D3, D5, D6, D8). Where the DIS-82 description differs from this group (criterion, allowed sources, output format), this group prevails.

**Input set.** The 40 answers of `docs/measurements/context/answers/acme-shop.json` (20, fixture `fixtures/acme-shop/`, PHP/Laravel) and `docs/measurements/context/answers/task-api.json` (20, fixture `fixtures/task-api/`, TypeScript/Fastify), each identified by `project` (the file's `fixture`) and `questionId` (`Q01`…`Q20`). Each answer gives `question`, `answer` (the text, or `UNKNOWN`), `reason` (only for `UNKNOWN`), `statements` (`text`, `type`, `evidenceIds`) and `evidence` (`file`, `startLine`, `endLine`, `excerpt`, paths relative to the fixture root). For each answer, the question's `expected` (`answer` or `unknown`, fixed before the answers existed) is in `docs/measurements/context/questions.json`. Judge every answer the same way; nothing in the input says how it was produced, and you must not try to find out.

**Criterion** (`docs/measurements/answer-review/criterion.md` is its Spanish rendering; where they differ, this paragraph prevails):

- Judge each answer only against the executable code of its fixture. Read `answer` and every `statements[].text`. An `evidence` excerpt is a pointer, not proof: check what is claimed in the fixture file itself. Executable code prevails over comments, docblocks and documentation.
- A claim about the content of a fixture file outside the allowlist (its `tests/`, `docs/` or `README.md`) is judged only by the behaviour it states, against the application code; that file is not read, and a claim that only states what such a file says, with no behaviour checkable in the application code, counts as a claim without support in the code.
- The *central claims* are the claims needed to answer the question as asked; every other claim is secondary. A hedged claim ("probablemente", "podría") is judged as a claim. The `type` label of a statement (`FACT`, `INFERENCE`) does not change how it is judged.
- `correct` — it answers the question asked, every central claim is supported by the code, and no claim of `answer` or `statements` is contradicted by the code.
- `partial` — the central claims are correct, but a secondary claim is false or has no support in the code, or the answer omits a part the question explicitly asks for.
- `incorrect` — a central claim is contradicted by the code, the answer addresses a different question, or it gives no answer.
- `UNKNOWN` answers (whatever their `reason`): for a question whose `expected` is `unknown`, `correct` when the fixture does not implement what is asked (cite the closest `file:line` that shows it, for example the route list or the service of that area) and `incorrect` when it does implement it; for a question whose `expected` is `answer`, `incorrect` (it does not answer), citing the code that answers the question.
- An answer with content to a question whose `expected` is `unknown`: `correct` if it says the fixture does not implement it and that is true; `partial` if it says so but adds a false secondary claim; `incorrect` if it asserts behaviour that does not exist in the code.
- Do not count: the language of the answer (Spanish or English), its style or length, nor whether the cited `evidence` is the best possible; only whether what it claims is true in the code.

**Output format.** One JSON object per reviewer, two-space indent:
`{ "reviewer": <1|2>, "model": "<your own model id>", "date": "YYYY-MM-DD", "sourcesRead": ["<repository-relative path of one file, or 'linear:DIS-82/description'>", ...], "answers": [ { "project": "acme-shop", "questionId": "Q01", "verdict": "correct" | "partial" | "incorrect", "reason": "<one to three sentences citing at least one file:line, path relative to the fixture root, e.g. app/<Dir>/<File>.php:<line> or src/<dir>/<file>.ts:<line>>" }, ... ] }`, with the 40 answers in order (`acme-shop` Q01…Q20, then `task-api` Q01…Q20). At least one citation of each reason must name an existing `.php`, `.ts` or `.json` file of the answer's fixture with a line between 1 and that file's last line; other citations are ignored. Each `sourcesRead` entry names one file (never a directory or a glob such as `fixtures/task-api/src/**`). The resolution is `{ "resolver": "<model id>", "date": "YYYY-MM-DD", "sourcesRead": [...], "answers": [...] }`, with no `reviewer` and no `model` field, and its `answers` hold only the disagreements, each in the same shape.

**Output paths.** Reviewer 1: `docs/measurements/answer-review/reviewer-1.json`. Reviewer 2: `docs/measurements/answer-review/reviewer-2.json`. Resolution of their disagreements: `docs/measurements/answer-review/resolution.json`. Agreement (recording agent, by the script): `docs/measurements/answer-review/agreement.json`.

**Allowed sources (allowlist).** Reviewers: `docs/measurements/answer-review/criterion.md`, `docs/measurements/context/answers/acme-shop.json`, `docs/measurements/context/answers/task-api.json`, `docs/measurements/context/questions.json`, files under `fixtures/acme-shop/app/`, `fixtures/acme-shop/routes/`, `fixtures/acme-shop/config/` and `fixtures/acme-shop/database/`, `fixtures/acme-shop/composer.json`, files under `fixtures/task-api/src/`, `fixtures/task-api/package.json`, `fixtures/task-api/tsconfig.json`, this `tasks.md`, `docs/base-standards.md` and the **description** of Linear DIS-82 (`get_issue` with default fields: no relations, never its comments). The resolver may also read `docs/measurements/answer-review/reviewer-1.json`, `docs/measurements/answer-review/reviewer-2.json` and `docs/AUTONOMOUS-RUN.md`; never `docs/measurements/answer-review/agreement.json`. Every file read goes in `sourcesRead`, one entry per file; a directory, a glob or a path outside the allowlist makes the output invalid.

**Forbidden sources.** Everything not in the allowlist, in particular: every other file under `docs/measurements/` (`docs/measurements/context/context-savings.csv`, `context-savings.json`, `docs/measurements/context/raw/**`, `docs/measurements/context-savings.md`, `docs/measurements/answer-review/agreement.json`, `verdicts.csv`, the other reviewer's output, and the DIS-80 and DIS-79 files); `readme.md`, `README.md`, `prompts.md`; `fixtures/README.md`, `fixtures/annotations/**`, `fixtures/acme-shop/README.md`, `fixtures/acme-shop/docs/**`, `fixtures/acme-shop/tests/**`, `fixtures/task-api/README.md`, `fixtures/task-api/docs/**`, `fixtures/task-api/tests/**`, `fixtures/task-api/node_modules/**`; `seeds/**`, `packages/**`, `scripts/**`, `tests/**`; `docs/**` otherwise (`docs/base-standards.md` and, for the resolver, `docs/AUTONOMOUS-RUN.md` are the only exceptions); `openspec/**` except this `tasks.md`; Linear comments of DIS-82 and any other ticket, and the ticket's relations. **Resolver and its step contract.** The general contract of your workflow step applies to git and commits only: you record no decision in `design.md` and write no Linear comment; you read neither `design.md`, the specs, the spec-audit report nor any Linear comment; every process document you read goes in `sourcesRead`. Derive the disagreements yourself from the two reviewer outputs (different `verdict` for the same `project` and `questionId`).

**Agreement measure** (design D4). Per project, n = 20: agreed answer = same `verdict`; percent agreement = agreed / n × 100, one decimal; unweighted Cohen's kappa over `verdict` (categories `correct`, `partial`, `incorrect`), three decimals, `null` when the expected agreement is 1.
