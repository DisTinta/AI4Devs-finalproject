## Goals / Non-Goals

**Goals:**

- A new answer for task-api `Q1`, produced once by the local generator, and a blind panel verdict on
  all seven items under the unchanged criterion, with the same record discipline as DIS-10 r2 and
  DIS-42 r2/r3 (criterion → regeneration → input → panel → resolution → signatures).
- The explain Purpose matches its requirements.

**Non-Goals:**

- No change to the generator, the prompt, the criterion, the seed or any product code. Improving the
  model's answer by other means (prompt, model, hand edit of the golden file) is out of scope.
- No regeneration of any golden answer other than task-api `Q1`.
- The DIS-110 round's files, including its `## Pending` sentence "no further round … follow", are
  history and are not rewritten.
- No new Linear ticket; DIS-110 stays Done.

## Decisions

### G1. Partial regeneration of task-api Q1, once per round

`npm run cache:build -- --project task-api Q1` with `LLM_BASE_URL=http://127.0.0.1:11434/v1`,
`LLM_MODEL=qwen2.5-coder`, `LLM_MODEL_VERIFY=qwen2.5-coder`, against the Ollama server the author
started with `OLLAMA_CONTEXT_LENGTH=16384` (the agent neither starts nor stops it). The command runs
once per round; its output is the round's answer, whatever it says. Only if the command itself fails
after its three internal attempts is it rerun once; a second failure stops the change for the author.
If `curl -s http://127.0.0.1:11434/api/tags` does not answer or does not list `qwen2.5-coder`, the
change stops before the criterion commit (destination C): the agent does not start Ollama.
*Alternative:* regenerate both projects: rejected, the other five answers were judged and signed by
DIS-110 and nothing changed their inputs.

### G2. Rounds: r2, then r3 only if task-api Q1 is still incorrect

r2 is the round of this change. If its final verdict for task-api `Q1` is `incorrect`, the change's
artifacts are updated first and the spec audit is re-run (always: the retarget changes requirements),
and r3 runs the same way. The r3 update: the delta is retargeted to `-dis-110-r3` with DIS-110 r2 as
one more previous round; the delta's "exactly one Criterion block" becomes two equal blocks (the r2
and r3 Panel groups) and the test's block count for the change's tasks file becomes 2; the r2 files
join the history (fifty SHA-256 files); groups 14–18 mirror groups 1–5 and run right after 5.6 (the
r2 history check is done before r3 starts) and before groups 6–13, so that the reports, docs and PR of groups 7, 11 and 12 describe the last round
(the DIS-42 r3 precedent). After r3
no further round follows: if task-api `Q1` is still `incorrect`, it stays unsigned, the r3 report
lists it under `## Pending`, and the change stops for the author (destination C). An `incorrect`
verdict on any other item stays unsigned and pending for the author; it does not start a round.

### G3. Signatures follow the latest round

Every entry whose r2 final verdict is `correct` or `partial` gets the two r2 signatures, replacing the
DIS-110 ones; an `incorrect` one gets `reviews: []`. This is the DIS-10 r2 and DIS-42 r3 rule.

### G4. The test is retargeted, not duplicated

`tests/unit/seed/golden-reviews.spec.ts` keeps one current round: its constants move to the
`-dis-110-r2` files and to this change (`CHANGE = 'golden-review-dis-110-r2'`; the tasks-file
resolution then finds `openspec/changes/golden-review-dis-110-r2/tasks.md` or the single archived
`*-golden-review-dis-110-r2/tasks.md`). `PANELIST_FILES` holds this change's active tasks path, the
r2 report and input, and `docs/base-standards.md`. The first DIS-110 round becomes one more previous
round: its report in `PREVIOUS_ROUND_REPORTS`, its panelist 1 file in `PREVIOUS_ROUND_PANELISTS`, and
`openspec/changes/archive/2026-10-30-pool-transaction-release/tasks.md` (one Criterion block) in
`PREVIOUS_ROUND_TASKS`, so the expected block counts become `[1, 3, 2, 1, 1, 1]`.

### G5. The explain Purpose

The `## Purpose` of `openspec/specs/explain/spec.md` is edited directly (a delta cannot change a
Purpose) in its own `docs(DIS-110)` commit (made by the author by hand after the hook denied the
agent's edit, and committed by the agent unchanged as `54bfc1d`, F4). New text:

> Answers a natural-language question about one indexed project: builds the context, asks the model
> for the answer, types each statement from the code it cites, stores it as a claim with its evidence
> and provenance, shows the stored claims that already cover that code, lazily refreshes the due stale
> prior claims with at most `MAX_STALE_REFRESHES` further model calls (requirement "Stale claim
> refresh"), and answers `UNKNOWN` with a reason instead of a plausible explanation when there is no
> anchor, no model or no evidence.

No requirement changes.

### G6. No ADR

The round follows existing practice (DIS-10 r2, DIS-42 r2/r3). No ADR.

### G7. Checking a panel output before recording it

The validation `it` reads both panelist outputs, so it cannot check one output alone. Before an
output is committed, only its key sets are checked against the Output format (a Node one-liner in the
scratchpad; the result goes to the step 7 report). Extra or missing keys → the same panelist re-emits
the same judgements without re-judging. Any other problem is never fixed by the agent: the output is
recorded as returned and the change stops under task 5.1 (destination C). If the returned text is not
parseable JSON, it is not recorded or repaired: the change stops under 5.1 (destination C) with the
raw text in the step 7 report. A re-emission is requested by resuming the same panelist agent; if it
cannot be resumed, the change stops (destination C).

## Risks / Trade-offs

- [The regenerated answer may be `incorrect` again] → G2: at most one more round, then the author.
- [The panel may change the verdict of an item it did not regenerate] → expected: the panel is blind
  and re-judges all seven; that item is signed or left pending by the r2 verdict (G3).
- [CI red on `golden-reviews.spec.ts` between the regeneration commit (2.4) and the signature commit
  (5.4): the DIS-110 input stops matching the golden file at the regeneration] → expected, as in
  every round; the window is recorded in the step 7 report.
- [The Ollama server was started by the author; its context length cannot be read back from the
  agent] → the agent records the `/api/ps` output after the run; it does not restart the server.
